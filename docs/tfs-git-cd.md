# Controlled TFS Git CD: approved IIS integration

The approved integration is implemented on Dev and **disabled by default**. No live IIS deployment, WinRM configuration change, migration application, commit or push was performed. Existing uncommitted work, including Home/Index.cshtml and Shared/_Layout.cshtml, was preserved. Prior phase notes below are historical and do not describe the current implementation.

## Implemented approval and execution path

Manual CI Builds → artifact → Prepare Deployment and deterministic Assistant commands resolve the same registered Portal / definition 1 / refs/heads/Dev / drop selection. `Deploy Portal latest Dev build on Deployment_1` and explicit build commands return the shared preparation page; they do not stage, Confirm or execute automatically. Existing manual Assistant commands remain available.

1. Local preparation retrieves validated Container files with guarded GET endpoints, bounded sizes, no redirects, no arbitrary URLs and no archive extraction. It pins build, full commit, repository, artifact/container identity, destination and SHA-256 hashes in a protected expiring record.
2. A separate antiforgery-protected **Prepare remote package** POST uses the existing PowerShell service and authenticated Negotiate WinRM session. The fixed `StageCd` operation transfers verified local files into an administrator-provisioned private remote root, under `<preparation-guid>/publish`. It validates protected ACLs, link-free ancestors/tree, filenames, file counts/sizes and received SHA-256 hashes. No IIS configuration, application pool or target files are modified during preparation. Failed/partial remote staging is retained privately for operator inspection; it cannot become reviewable.
3. Remote preparation supports **existing IIS application updates only**, at the registered physical path with a dedicated pool. Target settings are copied only into private staging. Artifact settings do not overwrite the target during preparation.
4. The shared preparation details POST the authoritative draft to the existing `/Deployments/Review`. Remote preflight validates the effective package and target configuration. The existing ten-minute protected confirmation token additionally binds a digest of the complete protected CD snapshot. The hidden preparation GUID is a reference, not authority; server-side validation reloads every execution parameter.
5. Human Confirm uses the existing `/Deployments/Create` POST and serializable queue transaction. A preparation can be consumed by only one deployment; repeat Confirm or multiple Review tokens return that same queued deployment. Antiforgery, token expiry, IIS/server fingerprint checks and the queue/worker boundary remain mandatory. Reserved CD paths cannot be submitted through a legacy form without provenance.
6. The existing worker reloads protected provenance and current registry/server/root policy. Disabling CD after approval fails closed before WinRM execution. The existing IIS script, backup, mutex and rollback execute the update; there is no separate CD deployment engine. Under its mutex, it checks source hashes, target configuration/runtime compatibility and unexpected target-only files before stopping the pool, and again before replacing files. Missing pools/targets cannot be repaired or created by CD.
7. CD success requires the script's read-only verification evidence: selected existing application, physical path, dedicated pool, started site/pool, effective deployed file hashes and preserved configuration hashes. Verification failure uses the existing failure/rollback path. Worker results without verification evidence cannot report CD success. **Application HTTP health is not checked.**

## Configuration preservation policy v1

`PreserveExistingRequired.v1` requires target `appsettings.json` and `web.config`. It preserves recursively all target JSON except code-generated `*.deps.json` / `*.runtimeconfig.json`, `.config`, `.xml`, `.yaml`, `.yml`, `.ini`, `.toml`, `.settings`, `.env*`, and common certificate/private-key extensions. This deliberately conservative policy may block packages with changing static JSON/XML data. Additional administrator-owned relative Windows paths can be registered in `SitesRegistry:Applications[].Destinations[].PreservedConfigurationFiles`; missing registered files fail closed. Do not put secret values in this registry.

Target-only files outside this preservation policy block preparation; operators must explicitly register preservation paths or manage those files outside CD. Newly introduced configuration/certificate files in the artifact also block preparation. No automatic JSON/XML merge or secret content display exists. Only paths, sizes and hashes enter manifests, Review and the protected database snapshot. Live IIS environment settings and bindings are not changed for updates.

Preserved web.config must match the artifact's ASP.NET Core processPath, arguments, hostingModel and handler configuration; the referenced package-local DLL/EXE must exist. Custom executable arguments are unsupported. Matching bounded target/package runtimeconfig runtimeOptions are required; framework upgrades, differing runtime options and unsupported/single-file layouts require operator review outside this CD policy. Configuration changes after preparation invalidate preflight/execution and require a new preparation and human confirmation.

## Feature flags, migration and remaining blockers

Tracked `tfs-cd.json` keeps `ExplorerEnabled=false`, `Enabled=false`, `ExecutionEnabled=false`, and both staging roots empty. ExplorerEnabled gates Explorer; Enabled gates local staging and Assistant artifact preparation; Enabled **and** ExecutionEnabled gate remote preparation, protected CD Review, queue validation and worker execution. Existing manual/PMSNZ behavior remains available with the defaults.

Additive migration `20261012170222_AddControlledCd` creates only `CdDeploymentSources` with protected snapshot, immutable display provenance, preparation/unique deployment linkage, approval and verification timestamps and sanitized stage audit. It is **generated, not applied**. Manual history/worker queries conditionally omit the new table until that migration exists; CD fails closed if it is absent. No existing tables are altered. Data-protection keys must remain protected and durable under the existing portal identity; key loss invalidates preparations safely.

Deployment details show queued/running/successful/failed status, source build/commit/artifact, approval, fixed audit stages, sanitized errors and recorded verification timestamp/evidence. Assistant status includes CD provenance and explicitly reports recorded history rather than a fresh live IIS probe. There is no application identity/RBAC integration; audit records portal human confirmation without inventing an individual approver identity.

Unresolved target VM WinRM authentication remains the live blocker. No WinRM/TLS/certificate bypass was added. Existing dev-only credential provider restrictions still apply. Private staging ACL provisioning, durable key permissions, SQL migration review/application and real target acceptance tests are operator prerequisites. Remote staging has fixed hard caps (256 MiB package, 64 MiB/file, 1,000 received files, ten retained preparation directories); effective manifest/configuration evidence is bounded and validated again in C#. Capacity fails closed; no automatic package cleanup is implemented. Do not delete preparations referenced by queued/running deployments.

## Read-only implementation

Explorer: CI Builds -> View artifacts -> Explore files on a completed/succeeded build. It uses the existing guarded GET-only client, no redirects, and the documented HTTP endpoint exception. Metadata is limited to 2 MiB / 10,000 entries with a 30-second body deadline. Unsafe paths, Windows collisions, incomplete items and out-of-root results fail closed. Folder navigation selects only folders in the validated listing and is never sent upstream. These limits protect inspection, not future extraction.

"Latest" does not mean "latest successful".
- `Check Portal deployment status`: queries the latest 100 deployment records for the registered site's application and server. Multiple destinations require `Check Portal deployment status on <registered hostname or display name>`. This is recorded history, not a live IIS probe.
- Existing `Deploy Portal on DEV server` still prepares the existing manual form and opens Review.
- TFS build deployment examples return an approval-pending error; they never fall through to manual deployment.

Queries return plain text and server-generated local detail links; the browser uses textContent and does not create a Review form for query results. The Assistant still uses antiforgery-protected POST. There is no LLM or executable command generation.
