# Sources Management (Phase 1B)

The existing `/Servers` page retains its server list/actions and includes Servers / Sources navigation. Sources opens `/Servers/Sources`. All Source actions, including forms, metadata, listing and connection tests, require the `SourcesManagement` policy. Configure approved SIDs independently as described in [SourcesManagementAuthorization.md](SourcesManagementAuthorization.md); this phase adds none. Credential provisioning remains host-only as described in [SourceCredentials.md](../tools/SourceCredentials.md).

The `AddInfrastructureSources` migration adds only the `InfrastructureSources` table, a unique provider/destination index and a rowversion concurrency token. It has been generated, not applied. Before use, an administrator must review and apply the migration through the normal database change process. Sources listing returns a generic availability response if its SQL schema/database is unavailable. Existing server actions do not query this table.

Add a display name, provider, approved URL and (for cloud providers) a selectable credential reference. The reference options contain only metadata verified against private NTFS permissions and the DPAPI binding. If metadata verification fails, no options are returned; configured TFS collections remain available. A malformed record invalidates metadata listing rather than exposing partial/unverified records. Metadata enumeration is capped at 256 records.

Azure DevOps URLs must be `https://dev.azure.com/{organization}/`; GitHub URLs must be `https://api.github.com/orgs/{organization}/`. A selected reference must match both the provider and canonical organization URL. The backend revalidates this on saves and connection tests. Enterprise/custom token endpoints are outside Phase 1A support. The source database stores references, never tokens.

TFS registrations are limited to valid existing `Tfs:BaseUrl` and `TfsGit:BaseUrl` collections. They use the existing protected Windows credential provider, primary HTTP handler and read-only Git request guard. No guard or existing CI/CD transport is modified. No new HTTP destinations are accepted; the existing approved internal HTTP endpoint exception is preserved. Configured collections display as deduplicated, read-only entries without importing database rows. A matching registration replaces that configured entry in the list. Deleting the registration makes the configured entry visible again and does not change appsettings or delete its host credentials.

Save, enable/disable, delete and test are antiforgery-protected POST actions. Disabled sources cannot be tested. Editing or toggling a source clears its stale test result. Tests perform one bounded read-only GET using fresh credentials: Azure DevOps lists at most one project; GitHub reads the bound organization; TFS lists at most one project. Redirects are not followed. Responses, exception details and credentials are not displayed or persisted; only a fixed status/message and UTC timestamp are stored. TFS additionally requires a JSON media type to avoid treating an HTML login page as success. Cloud response bodies are discarded by the existing credential resolver.

Successful testing verifies the selected API request, not access to every repository, project or deployment action. GitHub organization metadata may be public. No live provider request is made by automated tests, which use fakes and in-memory databases. Actual connectivity depends on configured host credentials, provider permissions, certificates and network access and should be verified by an authorized operator after database setup.

This feature registers infrastructure connections only; it does not select sources for CI/CD or change deployment workflows.
